## Етап 3. Серверні модулі й API

API використовує `/api/v1`; конкретний контракт, DTO та коди помилок фіксуються в API-01. Кожен endpoint викликає серверний сервіс, а не містить дубль бізнес-логіки.

- [ ] **API-01 · P0 — Описати API-контракти й валідацію.**
  Залежить від DB-01 і SETUP-01. Публічні catalog / banners / settings; захищені me / orders; admin catalog / orders / dashboard / content / settings. Визначити DTO, пагінацію, помилки, межі кількостей і довжин полів, формати телефону й грошей. Критерій: особисті та внутрішні поля не входять у публічні відповіді.
- [ ] **CAT-01 · P0 — Реалізувати категорії.**
  Залежить від DB-02, AUTH-02, API-01. CRUD, активність, порядок, захист видалення зайнятої категорії. Критерій: у публічному меню тільки активні категорії, правила їх доступності застосовуються і при checkout.
- [ ] **CAT-02 · P0 — Реалізувати товари.**
  Залежить від CAT-01. CRUD, пошук, фільтри, пагінація, активність, рекомендації, порядок, soft delete для товарів з історією. Критерій: ціна / вага додатні, категорія існує; товар із замовленням не видаляється фізично.
- [ ] **CNT-01 · P1 — Реалізувати банери, контакти та налаштування.**
  Залежить від AUTH-02, API-01, DB-02. CRUD банерів, контакти, delivery fee / threshold, зона, acceptingOrders. Критерій: UI й сервер користуються одними налаштуваннями; небезпечні посилання та недопустимі суми відхиляються.
- [ ] **ORD-01 · P0 — Реалізувати розрахунок кошика.**
  Залежить від CAT-02 і CNT-01. Актуальні ціни, доступність, сума товарів, доставка та total; нормалізація дубльованих позицій. Критерій: рівно на порозі доставка безкоштовна; сума не залежить від надісланих клієнтом цін, float-помилок чи порядку позицій.
- [ ] **ORD-02 · P0 — Реалізувати створення замовлення.**
  Залежить від ORD-01 і AUTH-02. Google session, контактна форма, перевірка приймання, повторна перевірка кошика, snapshot, транзакція, унікальний публічний номер, ідемпотентність. Критерій: конкурентні дублікати запиту створюють один Order; той самий ключ з іншим payload відхиляється; зміна ціни повертає кошик для повторного підтвердження.
- [ ] **ORD-03 · P0 — Реалізувати історію та деталі клієнта.**
  Залежить від ORD-02. Список із пагінацією та деталі тільки для власника. Критерій: відсутня можливість підставити чужий userId, внутрішні примітки не виходять клієнту.
- [ ] **ORD-04 · P0 — Реалізувати роботу оператора.**
  Залежить від ORD-02 і AUTH-02. Список, пошук, фільтри, деталі, переходи статусів, оплата, скасування, аудит. Критерій: недопустимі та конкурентні застарілі переходи відхиляються; completed вимагає paid, повторне завершення не дублює події.
- [ ] **STAT-01 · P1 — Реалізувати статистику.**
  Залежить від ORD-04. Агрегації в PostgreSQL за визначеннями плану, часові межі Europe/Kyiv, нульові продажі, архівовані товари. Критерій: cancelled / unpaid не збільшують виручку, один набір fixtures дає передбачувані показники всіх карточок.
- [ ] **SEC-01 · P0 — Перевірити захист API та завантажень.**
  Залежить від серверних модулів. Серверна авторизація, origin / CSRF, валідація, сталі ліміти зловживань, безпечні upload, мінімальні DTO, відсутність секретів у логах. Критерій: прямий HTTP-запит не обходить обмеження UI; rate limit не покладається лише на пам’ять одного serverless-процесу.
- [ ] **CACHE-01 · P1 — Налаштувати оновлення даних.**
  Залежить від CAT-02, CNT-01, ORD-03. Інвалідація каталогу / контенту після змін; приватні відповіді без публічного кешування. Критерій: деактивація відображається в меню, checkout завжди перевіряє базу, дані одного користувача не потрапляють іншому.

## Рекомендований порядок роботи

Це порядок продуктових залежностей. Для навчання після LEARN-00 спочатку опрацьовуємо потрібні основи JavaScript, TypeScript та асинхронності, підготовку середовища й простий HTTP-обробник, потім SQL та решту тем за [LEARNING_PLAN.md](./LEARNING_PLAN.md). Захищені зміни каталогу виконуються після AUTH; публічне читання можна опрацювати раніше як частину, не закриваючи весь CAT-модуль.

1. PLAN-01 → ARCH-01 → SETUP; окремо підготувати та погодити WF.
2. DB → AUTH → CAT / CNT → ORD; перевіряти бізнес-правила в міру реалізації.
3. Після WF-02: меню / кошик / checkout; після WF-04—WF-05: каталог і робоче місце оператора.
4. Історія, головна, банери, налаштування та статистика з відповідними погодженнями.
5. Повна перевірка сценарію → наповнення → розгортання → інструкція.

Перший робочий наскрізний результат: admin створює категорію й товар → клієнт входить через Google та оформлює доставку → оператор бачить замовлення → клієнт бачить його в історії. Повний MVP додатково включає всі підтверджені P1-задачі.
