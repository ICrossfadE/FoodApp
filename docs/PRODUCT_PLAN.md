# План застосунку доставки їжі

Статус: адаптивний інтерфейс v0.2 оформлено й перевірено в FRONT-02 за прямим дорученням користувача. У FRONT-03 прибрано сторінку огляду мокапів та верхній демонстраційний банер. Серверна логіка залишається наступною роботою. Перегляд: [MOCKUP_REVIEW.md](./MOCKUP_REVIEW.md).
Перший етап — FRONT-01 у [TASKS.md](./TASKS.md): агент створює Next.js, мокапи всіх сторінок без логіки та їх мобільні версії; після явного погодження відповідних макетів виконує фінальну стилізацію й анімації. Цей етап не включає навчання користувача; навчальний бекенд залишається наступною окремою роботою.
Оновлено: 2026-11-10. Повний перелік задач: [TASKS.md](./TASKS.md). Порядок навчання та розподіл роботи: [LEARNING_PLAN.md](./LEARNING_PLAN.md).

## 1. Підтверджені рішення

- Один ресторан доставки; спочатку адаптивний вебзастосунок, пізніше окремий мобільний клієнт.
- Next.js, TypeScript, shadcn/ui; PostgreSQL у Neon.
- Перегляд меню та формування кошика доступні всім. Надіслати замовлення можна тільки після входу через Google.
- Лише доставка; оплата при отриманні, без онлайн-еквайрингу.
- Доставка має фіксовану ціну та стає безкоштовною від заданої суми товарів.
- Після оформлення оператор телефонує клієнту для підтвердження деталей.
- Адміністратор керує товарами, категоріями, замовленнями, банерами, контактами та параметрами доставки.
- Перед реалізацією візуальної частини кожної групи сторінок потрібно показати тестові wireframe й отримати явне погодження користувача. Мовчання не є погодженням.
- Для інтерактивних елементів потрібні hover, focus-visible, active, disabled і loading стани, де вони застосовні.
- Проєкт є навчальним для користувача, який працює у Webflow, невпевнено володіє JavaScript та майже не має досвіду бекенду. Погоджено Node.js + TypeScript і 3–5 годин навчання на тиждень невеликими задачами; спочатку потрібні основи JavaScript для серверної роботи. Функціональність MVP зберігається; змінюється розподіл роботи.
- Агент повністю виконує фронтенд: верстку, компоненти, адаптивність, локальний UI-стан, клієнтське підключення API та UI-перевірки. Наявний процес погодження wireframe зберігається.
- Користувач виконує бекенд і роботу з даними: API, серверну конфігурацію, SQL/ORM, міграції, бізнес-правила, авторизацію, серверні тести й розгортання. Агент пояснює мету, видає невеликі задачі та перевіряє спроби; не реалізує цю частину наперед без прямого прохання користувача.

## 2. Пропонована архітектура

Один Next.js-проєкт із App Router: магазин, адмінпанель і серверна частина. Окремий NestJS-сервер на цьому етапі не потрібен.

- Серверні модулі: catalog, orders, users, auth, analytics, content, settings.
- Бізнес-логіка й доступ до бази відокремлені від React-компонентів та HTTP-обробників.
- Route Handlers `/api/v1` надають API для клієнтських операцій і майбутнього мобільного застосунку.
- Server Components можуть викликати серверні сервіси напряму: додатковий HTTP-запит до власного API не потрібен.
- PostgreSQL є спільним джерелом даних. Мобільний клієнт використовуватиме API, без прямого підключення до бази.
- Вебсесія не переноситься автоматично в мобільний застосунок: його OAuth, зберігання сесії та оновлення даних реалізуються окремим майбутнім етапом.

Рекомендовані інструменти, які потрібно перевірити на сумісність перед встановленням:

| Потреба | Рішення | Навіщо |
| --- | --- | --- |
| Інтерфейс | Next.js, React, TypeScript strict | Сторінки й сервер в одному проєкті |
| UI | Tailwind CSS, лише потрібні компоненти shadcn/ui | Єдині форми, діалоги, таблиці, навігація |
| База | PostgreSQL / Neon | Замовлення, зв’язки, агрегації |
| Доступ до бази | Prisma, підтримувана сумісна версія | Типізовані запити та міграції |
| Авторизація | Better Auth + Google OAuth + сумісний адаптер Prisma | Готове керування входом і сесіями |
| Валідація | Zod | Спільні схеми вхідних даних, серверна перевірка |
| Фото | Cloudinary, підключення на етапі медіа | Постійне зберігання фото товарів і банерів |
| Кошик | React Context / reducer + localStorage | Невеликий локальний стан без додаткового state manager |
| Перевірки | TypeScript, ESLint; Vitest і Playwright для критичних сценаріїв | Перевірка бізнес-логіки й наскрізного оформлення |
| Хостинг | Vercel для Next.js, Neon для PostgreSQL | Просте розгортання pet-проєкту |

Не встановлювати одночасно альтернативні ORM, бібліотеки авторизації чи state manager. Redis, черги, WebSocket, карти й окремий API-сервер у MVP не потрібні. Залежності додаються тільки під конкретну задачу. Для pet-демо перевірити чинні free-tier ліміти; перед реальним комерційним запуском — умови тарифів.

## 3. Сторінки клієнта

### Головна `/`

- Header: логотип, меню, кошик із кількістю, вхід / профіль.
- Hero зі слайдером активних банерів у заданому порядку; кнопки навігації та доступність із клавіатури. Автопрокрутка не обов’язкова.
- Рекомендовані товари: адміністратор позначає товари, а не алгоритм рекомендацій.
- Короткі умови доставки, повідомлення про тимчасову зупинку приймання замовлень.
- Footer: телефон із посиланням для дзвінка, адреса, години роботи, соціальні посилання, політика конфіденційності.

### Меню `/menu`

- Активні категорії у визначеному адміністратором порядку; початковий фільтр «Усі».
- Перемикання категорій без втрати кошика, вибрана категорія зберігається в URL.
- Карточка товару: зображення, назва, опис, вага в грамах, ціна, кнопка додавання та кількість у кошику.
- Повторне додавання збільшує кількість. Видалені, архівовані чи неактивні товари замовити неможливо.
- Для MVP окрема сторінка товару не потрібна: основна інформація є в карточці.
- Стани завантаження, помилки, відсутності меню та порожньої категорії.

### Кошик та оформлення `/cart`

- Список позицій, зміна кількості, видалення, сума товарів, доставка, підсумок.
- Кошик зберігається між перезавантаженнями в цьому браузері; між пристроями у MVP не синхронізується.
- Вхід через Google перед відправленням; після входу повернення до кошика без втрати позицій.
- Коротка форма: ім’я, телефон, адреса доставки; коментар необов’язковий. Ім’я підставляється з Google й редагується.
- Телефон обов’язковий: Google може не надати його. Email із Google не замінює телефон для оператора.
- Без карти, окремої реєстрації, пароля, платіжної форми та обов’язкового збереження адресної книги.
- Сервер перевіряє товари, доступність, ціни, кількості та параметри доставки. При зміні ціни показує оновлений кошик і просить повторно підтвердити суму.
- Повторний клік або повтор запиту не створює дубль замовлення.
- Після підтвердженого збереження — номер замовлення, підсумок і повідомлення «Замовлення отримано. Оператор зателефонує для підтвердження».
- При помилці кошик зберігається; при невизначеному результаті повторюється той самий ключ запиту.

### Профіль та історія `/account`, `/account/orders/[id]`

- Ім’я, email Google, контактний телефон, вихід з акаунта.
- Тільки власні замовлення: номер, дата, склад, підсумок, адреса і статус.
- Статус оплати відображається окремо від статусу виконання.
- Ручне оновлення / отримання актуальних даних при відкритті сторінки; live tracking у MVP не потрібен.
- Немає замовлень, сесія завершилась, доступ заборонено, замовлення не знайдено — окремі зрозумілі стани.

## 4. Адмінпанель

Вхід через Google. Роль `admin` призначається контрольованою серверною процедурою; звичайна реєстрація завжди створює клієнта. Приховування кнопок не замінює перевірки прав на сервері.

### Товари `/admin/products`

- Список, пошук за назвою, фільтри категорії й активності, пагінація.
- Створити, редагувати, активувати, деактивувати, архівувати / видалити.
- Поля: назва, фото й alt-текст, опис, ціна, вага, категорія, активність, рекомендація, порядок.
- Адмінська карточка / рядок має дії керування; кнопка «Додати в кошик» належить клієнтському вигляду.
- Товар із замовленнями архівується замість фізичного видалення. Видалення без історії потребує підтвердження.
- Завантаження фото має обмеження розміру й типу; при помилці старе фото не втрачається.

### Категорії `/admin/categories`

- Створення, редагування назви, активація / деактивація, зміна порядку кнопками вгору / вниз.
- Один товар належить одній категорії у MVP.
- Не можна фізично видалити категорію з товарами: спочатку перенесення товарів або деактивація.
- Неактивна категорія приховує її товари з публічного меню та робить їх недоступними для нових замовлень.

### Замовлення `/admin/orders`, `/admin/orders/[id]`

- Таблиця: номер замовлення, дата й час, ім’я, телефон, сума, статус виконання, статус оплати.
- Пошук за номером замовлення / телефоном, фільтри дат і статусів, пагінація; нові зверху.
- Деталі: товари з цінами на момент оформлення, кількості, адреса, коментар клієнта, внутрішня примітка оператора.
- Телефон клікабельний. Внутрішня примітка ніколи не повертається клієнтським API.
- Зміна статусу, причина скасування, фіксація оплати; журнал змін із часом та адміністратором.
- Оновлення списку вручну й фонове опитування тільки поки сторінка відкрита; без власного WebSocket-сервера.
- Склад і ціни вже оформленого замовлення в MVP не редагуються. Зміни за дзвінком: скасувати з причиною й попросити оформити заново; редактор замовлення — окрема опція.

### Дашборд `/admin`

- Фільтр періоду: сьогодні / 7 днів / 30 днів / довільні дати; початково 30 днів.
- «Виручка»: сума замовлень зі статусом `completed` і оплатою `paid`, включно з доставкою, за датою `paidAt` у вибраному періоді. Це не чистий прибуток.
- Кількість замовлень: усі створені в періоді; окремо завершені та скасовані.
- Найпопулярніший товар: найбільше проданих одиниць у завершених оплачених замовленнях за той самий період `paidAt`.
- Найменш популярний: найменше одиниць серед товарів, доступних у поточному меню, з урахуванням нульових продажів. Це не порівняння однакового часу експозиції.
- За однакових значень — стабільне сортування за назвою / ID; без продажів показати «Ще немає продажів», не вигадувати лідера.
- Історичні продажі архівованих товарів залишаються у виручці та звітах.

### Банери `/admin/banners`

- Створення, редагування, видалення з підтвердженням, активність, порядок.
- Зображення, alt-текст, заголовок, короткий текст, необов’язкове посилання / текст кнопки.
- Посилання перевіряються; небезпечні URL-схеми заборонені.

### Налаштування `/admin/settings`

- Контакти, адреса ресторану, години роботи як текст, соціальні посилання.
- Фіксована вартість доставки та сума для безкоштовної доставки.
- Опис міста / зони обслуговування; оператор підтверджує адресу вручну.
- Перемикач «Приймання замовлень» і текст повідомлення при зупинці.
- Автоматичний розклад відкриття та геозони не входять у MVP.

## 5. Правила замовлення та грошей

- Статуси: `new` → `confirmed` → `preparing` → `delivering` → `completed`.
- Із будь-якого незавершеного стану адміністратор може перейти в `cancelled` з причиною. Клієнт не змінює статуси самостійно.
- Оплата при отриманні: `unpaid` → `paid`. Завершення вимагає зафіксованої оплати; можна виконати однією серверною операцією.
- У MVP завершені й скасовані замовлення не відкриваються повторно; повернення коштів — поза обсягом.
- Ціни зберігаються цілими копійками, вага — цілими грамами; гривні форматуються тільки для UI. Початкове припущення: валюта UAH.
- `subtotal` — сума актуальних цін товарів × кількості. Якщо `subtotal >= freeDeliveryThreshold`, доставка дорівнює нулю; інакше застосовується `deliveryFee`.
- Порожній кошик, неціла / недодатна / надмірна кількість, недоступний товар і вимкнене приймання блокують оформлення на сервері.
- Конкретні ліміти довжини полів, кількості позицій і одиниць фіксуються в схемах валідації до реалізації API.
- Разом з Order зберігаються snapshot назви, ціни, ваги товару, адреси, контактів і вартості доставки. Зміни каталогу та налаштувань не змінюють попередні замовлення.
- Order та OrderItem створюються в одній транзакції. Унікальний ключ ідемпотентності прив’язаний до користувача й вмісту запиту.
- Час у базі — UTC, у UI та межах звітних періодів — `Europe/Kyiv`.

## 6. Початкова модель даних

| Сутність | Основні дані |
| --- | --- |
| User | ID, ім’я, email, підтвердження email, телефон, роль, дати |
| Account / Session / Verification | Сутності провайдера авторизації згідно з адаптером |
| Category | UUID, назва, slug, активність, порядок |
| Product | UUID, categoryId, назва, опис, imageUrl / assetId / alt, priceMinor, weightGrams, isActive, isRecommended, sortOrder, archivedAt |
| Order | UUID, унікальний публічний номер, userId, контактні snapshot, адреса, коментар, subtotalMinor, deliveryFeeMinor, totalMinor, status, paymentStatus, paidAt, idempotencyKey, requestHash, дати |
| OrderItem | orderId, productId, snapshot назви / ціни / ваги, quantity |
| OrderEvent | orderId, actorId, попередній / новий статус, дія оплати, причина / внутрішня примітка, дата |

Потрібні зовнішні ключі, унікальні обмеження, перевірки додатних сум / ваги / кількості та індекси для userId + createdAt, status + createdAt, paidAt і пошуку замовлень. Точна схема — результат задачі DB-01, а не готова міграція.

## 7. Уточнення вимоги SHA-256

SHA-256 — хешування, а не шифрування. Звичайний SHA-256 непридатний для зберігання паролів через швидкість перебору.

- У MVP паролів немає: вхід клієнтів та адміністраторів через Google, пароль Google застосунок не отримує й не зберігає.
- Якщо локальні паролі з’являться пізніше, використовувати Argon2id із сіллю; за вимоги саме сімейства SHA-256 — спеціально налаштований PBKDF2-HMAC-SHA256, не одиночний SHA-256.
- ID товарів: випадкові UUID, не SHA-256 від назви чи ціни. ID не є секретом і не замінює перевірки прав.
- SHA-256 доречний для fingerprint канонічного payload ідемпотентного запиту; це не захист персональних даних.

## 8. Вимоги до роботи агента та якості

- Перед реалізацією звірятися з [навчальним маршрутом](./LEARNING_PLAN.md). Серверні частини змішаних задач виділяти в навчальні кроки; фронтенд агент робить самостійно. Результати перевірки та поточний крок фіксувати в журналі навчання.
- TypeScript strict, без необґрунтованого `any`; типи / DTO не мають передавати секретні поля клієнту.
- Перед великими змінами читати актуальну офіційну документацію Next.js, UI та відповідної інтеграції; перевіряти сумісність версій.
- Використовувати семантичний JSX. Залишати змістовні коментарі до компонентів, функцій і великих секцій: відповідальність, неочевидні правила, причини рішень. Не дублювати кожен рядок словами.
- Додавати тільки потрібні shadcn-компоненти та залежності; не створювати окремі абстракції без потреби.
- Перевіряти права в кожній захищеній серверній операції; користувач бачить тільки власні дані, адміністратор — дозволені операції.
- HTTP-only secure cookies, перевірки origin / CSRF засобами auth та для мутацій; серверна валідація, обмеження зловживань оформленням і upload.
- Секрети — тільки на сервері, не в `NEXT_PUBLIC_*`, репозиторії чи логах; персональні дані не логувати без потреби.
- Фото не зберігати у локальній файловій системі serverless-хостингу; публічне завантаження заборонене.
- Інтерактивні елементи мають hover та видимий клавіатурний фокус. Touch не залежить від hover; поважати reduced-motion, давати назви кнопкам-іконкам.
- Після змін запускати релевантні перевірки; для зміни коду — typecheck і lint, перед завершенням етапу — build, для змін бізнес-логіки — її тести. Для змін тільки документації — перевірка посилань та узгодженості.
- Не писати тести, що просто повторюють статичну розмітку. Критичні: гроші, права, статуси, дублікати замовлення й оформлення.
- Після змін товарів / категорій / банерів інвалідувати відповідні кеші; особисті та адмінські дані не кешувати публічно.
- Замовлення та адмінські списки мають пагінацію; звіти рахуються в базі, не завантаженням усіх записів у браузер.

## 9. Процес погодження wireframe

1. Узгодити карту сторінок і правила замовлення з цього документа.
2. Показати прості wireframe першої групи: головна, меню, кошик / checkout; desktop і mobile, ключові порожні та помилкові стани.
3. Зафіксувати зауваження, внести правки, отримати явне погодження цієї групи.
4. Так само погодити профіль / історію та кожну групу адмінпанелі.
5. Лише після відповідного погодження реалізовувати фінальний UI цієї групи. Погодження інших сторінок автоматично не переноситься.
6. Якщо структура погодженого екрана суттєво змінюється, повторно показати wireframe зміненої частини.

Вихід етапу wireframe — артефакти для перегляду й журнал рішень, не готовий дизайн. До погодження можна працювати над невізуальними частинами: схемою бази, сервісами, авторизацією та тестами.

## 10. Що потрібно надати / визначити до відповідного етапу

- Назва ресторану, логотип, бажані кольори й приклади стилю — перед фінальним дизайном; wireframe можуть використовувати placeholders.
- Фіксована ціна доставки та поріг безкоштовної доставки — до завершення checkout. Значення не вигадувати; тестові позначати як демонстраційні.
- Місто / зона доставки, контакти, години роботи, валюта UAH і часовий пояс — до публікації. Геоперевірка адрес не входить у MVP.
- Google-акаунт першого адміністратора й спосіб контрольованого призначення ролі — до перевірки адмінпанелі.
- Фото, описи, категорії, банери, ціни й алергени за наявності — до наповнення каталогу.
- Дані доступу до Neon, Google OAuth, Cloudinary та хостингу — через захищений механізм секретів під час підключення, не в Markdown / чаті.
- Текст політики конфіденційності та контакти для запитів щодо персональних даних — до публікації.

## 11. Додаткові опції, які не входять у MVP

- Пошук товарів; алергени / гострота як фільтри; складні модифікатори й набори.
- Повторити минуле замовлення з перевіркою поточних цін та доступності.
- Редагувати склад підтвердженого замовлення з аудитом і повторним погодженням суми.
- Telegram / email-сповіщення оператору після окремого погодження сервісу та отримувача.
- PWA, синхронізований кошик між пристроями, збережені адреси.
- Промокоди, бонуси, онлайн-оплата, самовивіз, графік замовлення на певний час.
- Карта, геозони, автоматичний розрахунок маршруту, застосунок кур’єра, push-сповіщення.
- Інтеграція з POS ресторану, облік залишків і собівартості, чистий прибуток.
- Окремий мобільний застосунок зі спільним API й окремим етапом мобільної авторизації.

## 12. Критерій готовності MVP

Адміністратор створює категорію й товар із фото, налаштовує банер, контакти та доставку. Клієнт збирає кошик, входить через Google, залишає телефон і адресу та надсилає рівно одне замовлення. Оператор бачить його, зв’язується з клієнтом, проводить через статуси та фіксує оплату. Клієнт бачить власну історію, дашборд — узгоджені показники. Перевірки прав, грошей і повторних запитів проходять; погоджений UI працює на телефоні та desktop.
