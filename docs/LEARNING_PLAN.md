# План навчання бекенду на Food app

Оновлено: 2026-11-10. Статус: стартовий рівень, стек і темп уточнено; навчальна задача — LEARN-JS-01, спробу ще не перевірено. У FRONT-01 агент створив Next.js та адаптивні мокапи v0.1 всіх сторінок без навчальних завдань для користувача. У FRONT-02 за прямим дорученням користувача оформлено й перевірено інтерфейс v0.2; серверну частину не реалізовано.

Продуктові вимоги: [PRODUCT_PLAN.md](./PRODUCT_PLAN.md). Задачі реалізації та їхні критерії: [TASKS.md](./TASKS.md). Правила для наступних сесій агента: [AGENTS.md](../AGENTS.md).

## 1. Мета та незмінні умови

Навчитися самостійно створювати, пояснювати, перевіряти й розгортати бекенд на прикладі реального застосунку доставки їжі. Користувач працює у Webflow; це дає контекст інтерфейсів, але не означає впевненого знання JavaScript. Практичного досвіду бекенду майже немає.

Самооцінка користувача:

| Технологія / навичка | Рівень |
| --- | --- |
| JavaScript, React, Dart | Невпевнено |
| Node.js, TypeScript | Трохи |
| .NET (у відповіді «NET») | Трохи; конкретну мову та досвід не уточнено |
| async/await, fetch до API, Git | Невпевнено |
| HTTP, SQL, термінал | Окремо не перевірено; пояснюємо з основ у відповідній темі |

Це самооцінка, а не результат перевірки коду. Починаємо з коротких вправ із JavaScript для бекенду, додаємо типи та асинхронність поступово. React, Dart і .NET не додаємо як обов'язкові навчальні теми цього проєкту.

Усі погоджені можливості застосунку залишаються: меню, кошик, Google-вхід, доставка, замовлення, історія, адмінпанель, банери, налаштування та статистика. Навчання не скорочує MVP й не додає до нього нових продуктових функцій.

Погоджено Node.js + TypeScript. Стек з продуктового плану: Next.js App Router + TypeScript, PostgreSQL у Neon, Prisma, Better Auth із Google OAuth, Zod, Cloudinary, Vercel. Node.js — середовище виконання серверного JavaScript, а Next.js надає серверні обробники; окремий Express/NestJS-сервер для навчання не додаємо. Пояснюємо загальні принципи HTTP, SQL і серверної логіки, щоб знання переносилися на інші фреймворки.

Версії та сумісність перевіряємо перед встановленням у ARCH-01. Погоджений темп — **3–5 годин на тиждень, невеликі задачі**. Орієнтир: 2–3 практичні задачі по 25–45 хвилин, решта часу — пояснення, читання, перевірка й виправлення. Одночасно видаємо одну задачу; це не обов'язкова тижнева норма. Календарних дедлайнів і обіцянки строку готовності MVP немає: складність коригуємо за першими спробами.

## 2. Хто за що відповідає

| Частина | Користувач | Агент |
| --- | --- | --- |
| Верстка та UI | Переглядає й погоджує wireframe за чинним процесом | Повністю робить клієнтські сторінки, адмінку, компоненти, стилі, адаптивність, доступність і UI-перевірки |
| Клієнтський стан | Не отримує обов'язкових фронтенд-задач | Кошик, localStorage, форми, клієнтська валідація для зручності, loading/error/empty, запити до API |
| Серверний рендеринг | Вивчає серверні джерела даних і правила доступу | Робить JSX і відображення; серверне отримання даних опрацьовуємо як навчальну частину |
| API та дані | Проєктує й пише обробники, сервіси, серверну валідацію, запити й DTO | Пояснює, допомагає сформувати контракт, перевіряє рішення, підключає готові відповіді до UI |
| База й бізнес-логіка | SQL, схема, ORM, міграції, seed, гроші, доставка, транзакції, статуси | Дає послідовні задачі, перевіряє код і поведінку, пояснює помилки |
| Вхід і права | Серверна інтеграція готової auth-бібліотеки, сесії, ролі та перевірки | Пояснює потік, перевіряє захист, робить кнопки входу й UI-стани |
| Налаштування й експлуатація | Серверні env, база, OAuth, медіа, логи, тести, CI, deploy і відновлення | Супроводжує крок за кроком, пояснює кожну команду й перевіряє результат |
| Змішані задачі | Виконує серверну частину | Виконує фронтенд-частину; чітко відділяє її в описі задачі |

Клієнтська перевірка форми не замінює серверну. Відображення суми в кошику робить агент; остаточний розрахунок із актуальних даних на сервері — навчальна робота користувача. Прихована кнопка адмінки не замінює перевірку ролі на сервері.

Агент може підготувати фронтенд на явно позначених демонстраційних даних. Вони відповідають погодженому контракту, не видаються за робочу базу й замінюються готовим серверним джерелом. Продуктова задача з залежністю від бекенду не вважається завершеною, поки інтеграція не перевірена.

## 3. Як проходить одна навчальна задача

1. Агент називає проблему в застосунку й пояснює, навіщо її розв'язувати.
2. Дає мінімум теорії: нові терміни простою мовою, приклад на знайомому фронтенді, потрібне посилання на документацію. Без довгої лекції наперед.
3. Видає одну невелику практичну задачу: очікувана поведінка, місце роботи, що вже доступно, критерії та спосіб перевірки. Орієнтир — 25–45 хвилин, після перших задач адаптуємо. Якщо довго не виходить, розбираємо перешкоду й ділимо задачу, а не збільшуємо домашню роботу.
4. Користувач робить спробу в проєкті та повідомляє, що готово або де застряг. Не потрібно дублювати весь код у чаті, якщо він доступний у файлах.
5. Агент читає фактичний код, запускає доречні перевірки та пояснює результат: що працює, що потребує виправлення, чому і як це перевірити. Якщо запуск неможливий, окремо зазначає межі перевірки.
6. Користувач виправляє проблеми. Агент спочатку дає напрямок, потім конкретнішу підказку; повний розв'язок чи виконання замість користувача — на пряме прохання.
7. Коротка перевірка розуміння: пояснити рішення своїми словами або змінити одну умову. Це допомагає побачити прогалини, а не є іспитом.
8. Записуємо результат і наступний крок. Продуктову задачу закриваємо тільки після виконання всіх її критеріїв, а не після першої навчальної вправи.

Якщо виникла помилка, спочатку розбираємо повідомлення, відтворюємо її та перевіряємо припущення. Агент не переписує навчальний бекенд мовчки. Нову тему відкриваємо після готовності потрібних основ; тимчасову діагностичну вправу не підключаємо до production як завершений модуль.

## 4. Порядок тем і роботи

SQL-вправи етапу 3 виконуємо в окремій навчальній dev-базі; остаточний спосіб підключення й міграції належать до етапу 4. Частини CAT на етапі 5 — лише публічне читання, не завершення всього CRUD до авторизації. Точні контракти фіксуємо в API-01, а навчальний HTTP-обробник етапу 2 залишається окремою вправою.

Схему даних спочатку оглядаємо цілком, щоб бачити зв'язки, але складні частини детально розбираємо перед їх використанням. Не вимагаємо реалізації транзакцій чи ідемпотентності на першій задачі з таблицями.

Безпеку, тести та діагностику додаємо з першого релевантного endpoint; етапи 11 і 13 — системна перевірка та поглиблення. Наприклад, тести чужого доступу пишемо під час AUTH/ORD, а тести грошей — під час ORD-01. Медіа можна опрацювати раніше після AUTH-02, коли воно потрібне для завершення каталогу; решта тем етапу 11 зберігає свої залежності.

## 5. Контрольні результати

- **Після основ:** користувач сам пояснює, де виконується код, читає HTTP-запит і відповідь, знаходить помилку в простому обробнику.
- **Після даних і доступу:** створює міграцію, пояснює зв'язки й SQL, робить захищену операцію та доводить, що клієнт її виконати не може.
- **Після замовлень:** сам пояснює джерело істини для ціни, snapshot, транзакцію та захист від дублювання; перевіряє власність замовлення й статуси.
- **Після MVP:** може запустити чистий проєкт за інструкцією, внести невелику зміну в API та схему, додати перевірку, виконати міграцію й deploy та знайти причину помилки в логах.

Навчальна готовність і продуктова готовність відрізняються: розуміти тему недостатньо для закриття backlog, а скопійований робочий код ще не підтверджує розуміння.

За домовленістю від 2026-11-10 спочатку виконуємо FRONT-01 із [TASKS.md](./TASKS.md). Цей етап не включає навчання: Next.js, мокапи, мобільну адаптацію, а після погодження — фінальні стилі й анімації виконує агент. LEARN-JS-01 збережено як наступну навчальну задачу; її виконання не є передумовою FRONT-01. Навчальний бекенд у цей етап не входить.

Статус: задачу підготовлено; очікуємо першої спроби користувача. Орієнтир — 25–40 хвилин. LEARN-00 завершено як опитування; код і розуміння HTTP ще не перевірено.

**Пов'язана продуктова задача:** підготовка до ORD-01; вправа не закриває серверний розрахунок кошика.

**Навіщо:** сервер має вміти розрахувати вартість кількох одиниць товару. Починаємо з функції без бази, мережі й бібліотек, щоб зрозуміти вхідні дані та повернений результат.

**Мінімум теорії:** функція — іменований шматок коду, який можна викликати з різними даними. Параметри — назви цих даних усередині функції; `return` повертає результат у місце виклику. `console.log` лише показує значення для перевірки й не замінює `return`.

Приклад з іншою дією:

```js
function addOne(number) {
  return number + 1;
}

console.log(addOne(4)); // 5
```

`function` оголошує функцію; `addOne` — її назва; `number` — параметр. Під час виклику `addOne(4)` параметр отримує значення `4`. Символ `*` у JavaScript означає множення.

**Що зробити самостійно:** написати JavaScript-функцію `calculateLineTotal(unitPriceMinor, quantity)`, яка повертає вартість однієї позиції замовлення. `unitPriceMinor` — ціна одиниці в копійках; `quantity` — кількість одиниць. Наприклад, 129 грн — це 12900 копійок. Гроші зберігаємо цілими копійками, щоб уникати похибок дробових обчислень.

**Місце роботи:** звичайний JavaScript, для першої спроби достатньо консолі DevTools браузера на порожній вкладці (F12 → Console). Якщо браузер блокує вставлення, код можна набрати вручну. Можна також використати вже налаштоване JS-середовище. Встановлення Node.js та запуск проєкту розберемо окремо; це не прихована передумова цієї вправи. Результат можна надіслати кодом у чаті; якщо зберігаєш у проєкті — `learning/js/01-line-total.js`.

**Межі:** поки лише додатні цілі числа. Без TypeScript, об'єктів, масивів, доставки, перевірки помилкових значень чи створення сервера. Після перевірки додамо одну нову умову.

**Як перевірити:** викликати функцію через `console.log` з кожною парою аргументів:

| Ціна в копійках | Кількість | Очікуваний результат |
| --- | --- | --- |
| 12900 | 2 | 25800 |
| 8500 | 3 | 25500 |
| 4500 | 1 | 4500 |

**Критерії:** правильні результати для трьох прикладів; результат повертається через `return`; користувач може своїми словами пояснити обидва параметри й одиницю вимірювання результату.

**Що повідомити:** код функції, результати трьох викликів і що було незрозуміло. Необов'язково завершувати все перед зверненням по підказку.

**Результат перевірки:** ще не перевірено. Наступну задачу визначимо після спроби: прості умови для перевірки даних або додаткове пояснення функцій.
